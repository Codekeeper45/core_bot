AI-Оркестратор задач «Неодрэйн»

Автономный «ИИ-операционный директор»: принимает большую цель, раскладывает её на задачи, подбирает исполнителей, рассылает поручения в WhatsApp/Telegram, контролирует прогресс и отчитывается кто что сделал.

Node.js · CommonJS LLM: DeepSeek + OpenRouter WhatsApp · Telegram · Instagram MySQL 11 инструментов Простой и быстрый

1. Что это такое

Это не чат-бот «вопрос-ответ». Это диспетчер команды. Вы (босс) пишете ему задачу — он ведёт себя как проектный менеджер: анализирует, планирует, делегирует живым сотрудникам через мессенджер, следит за выполнением и отчитывается. Сотрудники общаются с тем же ботом как со своим «связным с руководством».

🎯 Принимает цель

Большую размытую задачу превращает в чёткий план с подзадачами, сроками и исполнителями.

👥 Делегирует

Сам выбирает кому поручить (по роли, навыкам и текущей загрузке) и пишет человеку в WhatsApp.

📡 Контролирует

Собирает отчёты сотрудников, считает прогресс, проактивно уведомляет босса.

⚡ Простой

Никакого скоринга, метрик и «обучения» — только чистый рабочий цикл. Быстро и предсказуемо.
Философия ядра: минимализм. Логика бота нейтральна и переиспользуема. «Личность» и поведение живут в одном текстовом промпте, инструменты — в отдельных файлах, штат — в базе. Чтобы изменить поведение, не нужно трогать код движка.

2. Общая картина

Сообщение от любого канала проходит единую обработку и попадает в «мозг» — агентный цикл с LLM, который умеет вызывать инструменты. Инструменты читают/пишут MySQL и отправляют сообщения людям.

          Telegram ┼──► [Нормализация] ─► [Медиа: голос→текст, фото→описание]
         Instagram ┘                                   │
                                                        ▼
   [Буфер ~1с] ─► [Антифлуд/дедуп] ─► [Блокировка чата]
                                                        │
                                                        ▼
                            ┌──────────  АГЕНТНЫЙ ЦИКЛ (LLM)  ──────────┐
                            │  системный промпт (босс/сотрудник)        │
                            │  + история чата + память организации      │
                            │  ↺ вызовы инструментов до 20 раундов      │
                            └───────────────────┬───────────────────────┘
                                                ▼
        Инструменты ──► MySQL (проекты, задачи, штат, память)
                   └──► Отправка людям (сотрудник / босс / менеджер)
                                                ▼
                                  [Ответ обратно в исходный канал]

3. Два режима: босс и сотрудник

Ключевая идея: один и тот же бот ведёт себя по-разному в зависимости от того, кто пишет. Перед каждым ответом бот смотрит, есть ли отправитель в реестре сотрудников (по паре канал + chat_id).

ПризнакРежим БОССА (оркестрация)Режим СОТРУДНИКА (отчёт)
Кто пишетЛюбой, кого нет в реестре сотрудников (или номер из BOSS_CONTACTS)Тот, чей контакт есть в таблице orch_employees
Что делает ботАнализ → план → делегирование → контроль → отчётПринимает статус по задаче, отвечает одной строкой
Доступные инструментыВсе: создание проектов, управление штатом, память…В основном update_task и message_boss
Подгружает в промптБлок «Организационная память» (уроки, решения, профиль босса)Блок «Employee context» (его открытые задачи)
Важный нюанс: если реальный босс пишет с WhatsApp-номера, который тоже числится в штате, бот примет его за сотрудника. Решение — добавить его номер в переменную BOSS_CONTACTS: она принудительно делает контакт «боссом». Из Telegram такой проблемы обычно нет.

4. Путь сообщения (пайплайн)

Каждое входящее сообщение проходит цепочку проверок по порядку (файл src/index.js):

Нормализация. Разные форматы WhatsApp/Telegram/Instagram сводятся к единому объекту {канал, chat_id, телефон, тип сообщения, текст…}.
Предобработка медиа. Голосовое → транскрипт (STT). Картинка → текстовое описание (Vision). Документ → извлечённый текст.
Буфер ~1 секунда. Если человек шлёт несколько сообщений подряд, они склеиваются в один запрос — бот не отвечает на каждое слово отдельно.
Антифлуд и дедупликация. Защита от спама и повторов (в памяти процесса).
Блокировка чата. Один активный запрос на чат; остальное ждёт в очереди (чтобы не было гонок).
Анализ изображений. Буферизованные картинки прогоняются через Vision.
Агентный цикл. Главная работа — LLM с инструментами (см. ниже).
Ответ. Результат уходит обратно в тот же канал, откуда пришёл.

5. Агентный цикл и LLM

Сердце бота (src/agent/agent.js) — это цикл «вызвать LLM → выполнить инструменты → снова вызвать LLM», пока задача не решена (до AI_MAX_ITERATIONS = 20 раундов).

Что получает модель на входе

  • Системный промпт — роль, стиль, правила (босс или сотрудник).
  • История чата из MySQL (последние ~100 сообщений; старое сворачивается в краткую сводку).
  • Организационная память (только для босса): релевантные уроки и прошлые решения.
  • Список инструментов с их описаниями.

Цепочка провайдеров с резервом (fallback)

Чтобы бот не падал при сбое одного провайдера, запрос идёт по цепочке — у каждого свои ретраи:

DeepSeek (основной)  ──► OpenRouter (primary)  ──► OpenRouter (backup)
deepseek-v4-pro          deepseek/deepseek-v4-pro     qwen/qwen3.7-max

Резерв предусмотрен для всех типов моделей:

НазначениеОсновная модельРезервная
Текст (агент)deepseek-v4-proqwen/qwen3.7-max
Распознавание речи (STT)openai/whisper-large-v3-turbogoogle/chirp-3
Распознавание картинок (Vision)google/gemini-3.1-flash-liteqwen/qwen3.5-flash
Если все провайдеры недоступны — бот честно эскалирует диалог на живого менеджера, а не отвечает мусором.

Авто-эхо действий

Чтобы было сразу видно, что делает бот, перед каждым раундом вызова инструментов он шлёт в чат короткую строку с действиями, например:

🗂 Составляю план «Лендинг Дренаж-Про» (5 задач)
📋 Смотрю список сотрудников и их загрузку
📨 Отправляю задачу #12 исполнителю
✏️ Обновляю задачу #12 → статус «done»

Это человекочитаемое эхо (не сырой JSON вызова). Управляется переменной ECHO_TOOL_CALLS (по умолчанию включено; выключить — ECHO_TOOL_CALLS=0).

6. Инструменты (11 шт.)

Инструменты — это «руки» бота. Каждый — отдельный файл в src/tools/, подключается автоматически. Модель сама решает, какой и когда вызвать.

Оркестрация

ИнструментЧто делает
list_employeesОтдаёт весь штат одним вызовом: роли, навыки, контакт и число открытых задач (для балансировки нагрузки).
create_projectСоздаёт проект + все подзадачи + план за один вызов. Проект сразу попадает в статус awaiting_approval — задачи НЕ рассылаются до утверждения.
assign_taskНазначает/переназначает исполнителя. При переназначении уже разосланной задачи сбрасывает флаги доставки и возвращает её в очередь (нужен повторный диспатч).
dispatch_taskШлёт сотруднику бриф в его канал. Блокирует отправку, если у задачи есть невыполненные зависимости (защита критического пути).
update_taskМеняет статус/результат задачи. Авторизация: сотрудник может трогать только свою задачу; босс — любую. Пересчитывает статус проекта и шлёт уведомление боссу.
project_statusПолный срез плана: задачи, исполнители, блокеры, невыполненные зависимости, счётчики. Без id — ВСЕ планы системы (босс — админ, видит планы любых владельцев/чатов).
revise_projectПересмотр плана по возражению/правке босса: обновить план, добавить/переназначить задачи. (Адаптация плана — часть планирования.)

Контроль и коммуникация

ИнструментЧто делает
message_bossСотрудник→босс: пересылает руководителю вопрос/проблему/возражение сотрудника.
message_employeeБыстро написать сотруднику вне задач: одному по id/имени/роли, либо ВСЕМ по роли (to_all, напр. «всем кладовщикам»). Для рабочих задач — create_project + dispatch_task.
manage_employeesБосс правит штат прямо в чате: добавить/изменить/удалить (или прислать новый список). Телефоны нормализуются автоматически.
get_current_timeТекущая дата/время (для дедлайнов и отчётов).
Сознательно НЕТ: никаких инструментов памяти/обучения и профилей-скоринга (recall_memory, remember_memory, employee_profile убраны). Бот выбирает исполнителей по роли/навыкам и текущей загрузке, а не по «рейтингу надёжности».

6+. Каждый инструмент подробно

Ниже — спецификация всех 11 инструментов: назначение, параметры (которые подаёт модель), что возвращается боту, когда он вызывается и какие побочные эффекты. «Реж.» = в каком режиме обычно используется (Б — босс, С — сотрудник).

📋 list_employees — реестр сотрудников · Реж.: Б

Назначение: отдать весь активный штат с ролями, навыками и текущей загрузкой — чтобы бот выбрал исполнителя и сбалансировал нагрузку до распределения задач.

Параметры: нет.

Возвращает: employees[], по каждому: id, name, roles, skills, open_task_count и open_tasks[] (id/название/статус каждой открытой задачи — готовые task_id для update_task/assign_task; так босс может «разгрузить» любого сотрудника), is_test (true = нет реального контакта, диспатч не уйдёт физически).

Когда: в начале планирования и перед назначением/переназначением.

Побочных эффектов нет (только чтение).

🗂 create_project — создать проект + задачи · Реж.: Б

Назначение: за один вызов создать проект и все его подзадачи с зависимостями и планом. Создаётся в статусе awaiting_approval — задачи НЕ рассылаются.

ПараметрТипОбяз.Описание
titlestringдаКороткое название проекта.
goalstringдаИсходная цель целиком, как сформулировал босс.
planstringнетПлан: порядок, критический путь, что параллельно, блокеры.
tasks[]arrayдаПодзадачи. У каждой: ref (врем. id, напр. «t1»), title, description, expected, priority (1–5), depends_on (массив ref), assignee_id.

Возвращает: project_id, status: awaiting_approval, tasks[] (карта ref→реальный id), warnings[] (если снят несуществующий исполнитель, пропущена неизвестная зависимость или разорван цикл).

Когда: после анализа и list_employees, когда ясны scope и результат. В быстром режиме — для одной задачи.

Эффекты: пишет проект и задачи в БД (атомарно, в транзакции); строит DAG, автоматически убирает циклы; валидирует исполнителей.

👤 assign_task — назначить/переназначить · Реж.: Б

Назначение: назначить или сменить исполнителя задачи (при блокировке/перегрузке).

ПараметрТипОбяз.Описание
task_idintegerдаid задачи.
employee_idintegerдаid нового исполнителя.

Возвращает: assignee (id+имя), новый status задачи, project_status, needs_redispatch (true → надо снова продиспатчить).

Когда: переброс задачи на другого человека.

Эффекты: при переназначении уже разосланной/завершённой/заблокированной задачи сбрасывает флаги доставки (dispatched/sent) и возвращает её в очередь (todo), а проект при необходимости переоткрывает (пересчёт статуса).

📨 dispatch_task — отправить задачу исполнителю · Реж.: Б

Назначение: физически отправить бриф по задаче назначенному сотруднику в его канал.

ПараметрТипОбяз.Описание
task_idintegerдаid задачи.
messagestringдаКороткий actionable бриф (цель, что сделать, результат, дедлайн).

Возвращает: dispatched, sent (true — реально доставлено; false — тестовый сотрудник без контакта), employee, либо отказ reason: blocked_by_deps + waiting_on[].

Когда: после утверждения плана (или сразу в быстром режиме), по одной задаче без блокеров.

Эффекты: гейт зависимостей — не отправит, пока предшественники не done; помечает задачу dispatched, фиксирует время диспатча; шлёт сообщение человеку в WhatsApp/Telegram.

✏️ update_task — статус/результат задачи · Реж.: С (и Б)

Назначение: зафиксировать прогресс по задаче. Основной инструмент в режиме сотрудника.

ПараметрТипОбяз.Описание
task_idintegerдаid задачи.
statusenumдаtodo / in_progress / blocked / done / reassign.
resultstringнетИтог/результат по задаче.

Возвращает: новый status, project_id, пересчитанный project_status.

Когда: сотрудник пишет «взял/готово/застрял»; босс может форсировать статус.

Эффекты: авторизация — сотрудник может менять только свою задачу (босс — любую); пересчитывает статус проекта одним агрегатом; проактивно уведомляет босса о прогрессе.

📊 project_status — срез проекта · Реж.: Б

Назначение: получить полный статус проекта или список проектов босса.

ПараметрТипОбяз.Описание
project_idintegerнетid проекта. Без него — список проектов этого чата.

Возвращает: project (цель, план, статус), tasks[] (исполнитель, статус, зависимости, результат, флаги доставки), summary (счётчики по статусам, блокеры, unmet_dependencies, сколько done).

Когда: контроль прогресса, сборка итогового отчёта.

Побочных эффектов нет (только чтение).

♻️ revise_project — пересмотр плана · Реж.: Б

Назначение: адаптировать план по возражению/правке босса: обновить план, добавить и/или переназначить задачи.

ПараметрТипОбяз.Описание
project_idintegerдаid проекта.
notestringдаСуть возражения/фидбэка (для пояснения).
planstringнетНовый текст плана.
add_tasks[]arrayнетНовые подзадачи (как в create_project).
reassign[]arrayнетПереназначения [{task_id, employee_id}].

Возвращает: plan_updated, added[], reassigned[], warnings[].

Когда: босс не согласен с планом / просит перераспределить.

Эффекты: правит план и задачи в БД. Возражение в память НЕ сохраняется (памяти нет).

📤 message_boss — сотрудник → босс · Реж.: С

Назначение: переслать руководителю вопрос/проблему/возражение/просьбу сотрудника, которые бот не решает сам.

ПараметрТипОбяз.Описание
messagestringдаСуть сообщения сотрудника для босса.
kindenumнетquestion / problem / objection / request.

Возвращает: routed_to: boss, project, note (доставлено/нет).

Когда: только в режиме сотрудника, когда нужен ответ руководителя.

Эффекты: определяет владельца проекта сотрудника и шлёт ему сообщение в его канал.

✉️ message_employee — быстрое сообщение сотруднику(ам) · Реж.: Б

Назначение: быстро написать сотруднику что-то вне рабочих задач — напоминание, просьбу, информацию. Одному или сразу всем по роли. (Для постановки задач — create_project + dispatch_task.)

ПараметрТипОбяз.Описание
tostringдаКому: id / имя / роль (напр. «Директор», «кладовщик», «Мякота», «6»).
messagestringдаТекст сообщения.
to_allbooleanнетtrue = отправить ВСЕМ подходящим по роли (рассылка). По умолчанию — одному.

Возвращает: count (скольким доставлено), total, sent_to[] ({id, name, sent}); либо отказ reason: no_recipient, если по запросу нет никого с контактом.

Когда: «напомни директору про…», «напиши всем кладовщикам…», «сообщи бухгалтеру…».

Эффекты: шлёт сообщение через notifier в канал(ы) получателей (обычно WhatsApp).

Как бот выбирает, КОМУ написать (to / to_all)

  1. Бот сам формирует строку to из запроса — id, имя или должность/роль («Директор», «кладовщик», «Елисеев», «6»).
  2. Система ищет в реестре orch_employees: число → по id; иначе нечёткий поиск (LIKE) по name / roles / skills.
  3. to_all=false (по умолчанию) → берётся ПЕРВЫЙ подходящий с контактом. to_all=true → сообщение уходит ВСЕМ подходящим с контактом (рассылка по роли, напр. всем 5 кладовщикам).

Пример. Босс: «Напомни всем кладовщикам про инвентаризацию в 9:00». Бот вызывает message_employee(to:"кладовщик", message:"Инвентаризация в 9:00", to_all:true) → сообщение уходит всем кладовщикам с контактом.

Нюансы:
  • Без to_all при широком запросе («менеджер») напишет одному (первому по id); для точечного — укажи имя или узкую роль.
  • У получателя должен быть контакт — иначе он пропускается.
  • Поиск по тексту полей штата (см. list_employees).

🛠 manage_employees — правка штата · Реж.: Б

Назначение: добавить / изменить / удалить (деактивировать) сотрудников прямо из чата.

ПараметрТипОбяз.Описание
actionenumдаadd / update / remove.
employees[]arrayдля addНовые: name, roles, skills, phone.
querystringдля update/removeid / имя / роль сотрудника.

7. Жизненный цикл проекта и задачи

Статусы проекта

awaiting_approval создан, ждёт утверждения босса   →  active в работе   →  blocked есть блокер   →  done завершён

Статусы задачи

todo в очереди   dispatched отправлена сотруднику   in_progress взял в работу   blocked заблокирована   done выполнена   reassign на переназначение

Типичная траектория

Босс ставит задачу → бот делает create_project → проект awaiting_approval.
Бот показывает план и ждёт «утверждаю».
После утверждения → dispatch_task по каждой задаче без блокеров → сотрудники получают брифы.
Сотрудник пишет «сделал» → update_task(done) → боссу летит уведомление, статус проекта пересчитывается.
Когда все задачи done → проект done → итоговый отчёт боссу кто что сделал.
Про утверждение (approval-first): требование «сначала показать план, потом рассылать» сейчас реализовано на уровне инструкции в промпте (по решению владельца), а не как жёсткий код-замок. Бот обучен показывать план и ждать подтверждения. Если нужна аппаратная гарантия — это отдельная доработка (добавить код-блокировку в dispatch_task).

8. Зависимости и план

Подзадачи могут зависеть друг от друга — это задаёт порядок выполнения и критический путь. При создании проекта зависимости указываются временными метками (ref, напр. «t1», «t2»), которые бот превращает в реальные id.

Что гарантирует система

  • Гейт зависимостей: dispatch_task не отправит задачу сотруднику, пока её предшественники не в статусе done. Вернёт blocked_by_deps со списком, кого ждём.
  • Защита от циклов: если в зависимостях случайно возник цикл (t1→t2→t1), система обнаружит его, отбросит замыкающее ребро и предупредит боса (в поле warnings).
  • Валидация исполнителя: если указан несуществующий assignee_id — назначение снимается с предупреждением, а не молча ломает диспатч.
Пример плана (как его строит бот внутри create_project):

t1  Исследование рынка        → assignee: Аналитик     зависит от: —
t2  Прототип интерфейса        → assignee: Дизайнер     зависит от: t1
t3  Бэкенд API                 → assignee: Бэкенд       зависит от: t1
t4  Интеграция фронт+бэк       → assignee: Фронтенд     зависит от: t2, t3
t5  Тестирование               → assignee: QA           зависит от: t4

Критический путь: t1 → (t2,t3 параллельно) → t4 → t5
t2 и t3 можно делать одновременно после t1.

9. Память (намеренно простая)

Бот не ведёт «организационную память» и не обучается — это убрано ради простоты и скорости. Никакой семантической/векторной памяти, ретроспектив, профилей надёжности и скоринга сотрудников.

Единственная память бота — история текущего диалога (таблица bot_chat_history): последние ~100 сообщений, при переполнении старое сворачивается в краткую сводку. Это нужно, чтобы бот держал контекст внутри одного разговора.

Чтобы начать новую задачу «с чистого листа», босс отправляет команду /new — история диалога стирается. Проекты и задачи в БД при этом сохраняются (см. Команды чата).
Выбор исполнителя происходит по роли/навыкам из list_employees и текущей загрузке (open_task_count) — просто и прозрачно, без вычисляемых рейтингов.

14. Безопасность

  • SQL-инъекции: все запросы параметризованы; имена колонок — из белых списков.
  • Авторизация задач: сотрудник не может закрыть чужую задачу через update_task.
  • Изоляция сбоев: ошибка БД отличается от «не найдено» (бот говорит «временный сбой», а не врёт).
  • Маскирование: в логах/ответах маскируются телефоны, карты, ИИН.
Зона внимания: текст, который босс/сотрудник сохраняет в память, позже подставляется в промпт. Это потенциальный вектор «stored prompt injection» — в мульти-боссовом сценарии стоит добавить разметку «недоверенного» контента. Для одной организации риск низкий.

16. FAQ и траблшутинг

Бот принимает меня за сотрудника, хотя я босс

Ваш WhatsApp-номер есть в реестре штата. Добавьте его в BOSS_CONTACTS в .env — тогда вы всегда будете «боссом». Либо пишите боту из Telegram.

Бот разослал задачи без моего утверждения

Утверждение реализовано через инструкцию в промпте. В редких случаях модель может поспешить. Если нужна жёсткая гарантия — закажите доработку: код-блокировку диспатча до явного утверждения.

Сотрудник не получил поручение

Проверьте: (1) у него заполнен контакт в orch_employees; (2) WhatsApp привязан (страница /pair); (3) в ответе dispatch_task поле sent. Если sent=false и помечен как «тестовый» — у сотрудника нет реального контакта.

Задача «висит» и не отправляется

Скорее всего у неё есть невыполненные зависимости (blocked_by_deps). Она уйдёт автоматически, когда предшественники будут закрыты. Проверьте через project_status → unmet_dependencies.

Бот не помнит прошлые проекты / не учится

Так и задумано. Бот намеренно простой: организационной памяти и обучения нет. Он держит контекст только внутри текущего диалога (история чата). Все проекты и задачи при этом сохраняются в БД и доступны через project_status.

Как начать с ботом новую задачу «с чистого листа»

Отправьте боту команду /new (или /новый, /сброс, /reset, /clear). Бот сотрёт историю переписки этого чата и подтвердит. Проекты и задачи при этом сохраняются — стирается только контекст разговора, чтобы новая тема не путалась со старой.

Изменил код/настройки — ничего не поменялось

Нужен рестарт контейнера. По договорённости его выполняет только владелец.

📜 Приложение A. Полный системный промпт

Дословно то, что бот получает в качестве инструкции. Состоит из базового промпта (он же режим босса) плюс, для зарегистрированного сотрудника, дописываемого блока EMPLOYEE CONTEXT. Базовый промпт лежит в src/agent/prompts/system_prompt.txt, блок сотрудника формируется в src/agent/systemPrompt.js.

A.1. Базовый промпт (режим БОССА)

Отправляется ВСЕГДА. Если блока EMPLOYEE CONTEXT нет — бот работает как оркестратор для босса.

Вы — AI-оркестратор выполнения задач: project manager и диспетчер команды. Вы не «чатик» и не
ассистент-болтун. Вы принимаете большую задачу/цель, анализируете её, сами решаете каких
специалистов нужно привлечь, декомпозируете работу, строите план, распределяете подзадачи между
сотрудниками, контролируете выполнение и выдаёте итоговый отчёт кто что сделал.

# СТИЛЬ
- Системно, рационально, кратко, уверенно, ориентировано на выполнение. Без воды и эмоций.
- Простой текст БЕЗ Markdown (никаких *, _, #, ```), мессенджеры ломают разметку.
- НИКОГДА не используй таблицы — ни markdown с символами | , ни ASCII-столбцы/псевдографику.
  Мессенджеры показывают их как кашу. Вместо таблицы — короткие строки или маркированный список
  (одна сущность = одна строка, поля через тире или двоеточие).
- Структурируй ответ: короткие списки, id задач, статусы, исполнители.
- Отвечай на языке пользователя.

# ДВА РЕЖИМА РАБОТЫ
Если в контексте есть блок «EMPLOYEE CONTEXT» — это пишет СОТРУДНИК. Режим приёма отчёта:
- Трактуй сообщение как обновление по одной из его открытых задач.
- Сопоставь сообщение с конкретным task_id и вызови update_task
  (status: in_progress / blocked / done; при наличии — result).
- Вопрос/проблему/возражение сотрудника, которые ты не решаешь сам, передай боссу через message_boss.
- Ответь ОДНОЙ строкой-подтверждением. Не запускай проекты, не задавай лишних вопросов.

Иначе это БОСС. Режим оркестрации (пайплайн ниже).

Если задача слишком большая, неоднозначная или рискованная (непонятен scope, нет критерия успеха,
нет дедлайна/ограничений, есть необратимые действия) — сначала задай МИНИМАЛЬНЫЙ набор уточняющих
вопросов и остановись. Не строй план на догадках. Переходи к create_project только когда ясны
scope, ожидаемый результат и ограничения.

# БЫСТРЫЙ РЕЖИМ (повседневные задачи) — определяй АВТОМАТИЧЕСКИ
Сначала оцени масштаб запроса босса:
- ПРОСТАЯ повседневная задача = один исполнитель, одно понятное действие, низкий риск, без
  многошаговой декомпозиции и зависимостей (напр. «поручи Тимуру починить баг на оплате»,
  «напомни Лене прислать макет к 18:00», «попроси Аиду обновить отчёт»).
  → РАБОТАЙ БЫСТРО, без церемоний — пропусти декомпозицию, DAG и этап утверждения:
    1) возьми исполнителя по имени/роли (при необходимости глянь list_employees);
    2) вызови create_project с ОДНОЙ задачей (title = суть, одна task с assignee_id);
    3) СРАЗУ вызови dispatch_task по ней — утверждения НЕ жди;
    4) ответь боссу одной строкой: кому и что отправил (+ срок, если был).
  Если непонятен исполнитель или суть — задай ОДИН уточняющий вопрос, не раздувай процесс.
- КРУПНАЯ / сложная / неоднозначная / рискованная задача (несколько шагов, зависимости, несколько
  исполнителей, важные последствия) → полный ПАЙПЛАЙН ОРКЕСТРАЦИИ ниже (с планом и утверждением).
Не превращай простое поручение в проект с кучей подзадач. Минимализм — это эффективность.

# ПАЙПЛАЙН ОРКЕСТРАЦИИ (для КРУПНЫХ/сложных задач, по порядку)
1. Проанализируй задачу: что нужно, масштаб, риски, тип, зависимости, критические точки.
2. Определи какие роли нужны. Не плоди лишних ролей, минимизируй число участников, используй
   мультироль-сотрудников где возможно.
3. Вызови list_employees (реестр + текущая нагрузка open_task_count). Назначай по роли/навыкам и не
   перегружай — отдавай задачи тем, у кого меньше открытых задач.
4. Декомпозируй задачу на подзадачи. Каждая: цель, описание, ожидаемый результат, приоритет,
   зависимости, исполнитель. Избегай giant-задач; делай их measurable и executable; минимизируй
   зависимости; максимизируй параллельность; никаких размытых формулировок.
5. Построй план выполнения: порядок, критический путь, что параллельно, какие блокеры.
   Зависимости должны образовывать DAG (без циклов).
6. Вызови create_project (title, goal, plan, tasks[] с ref/зависимостями/assignee_id). Проект
   создаётся в статусе ожидания утверждения — задачи ПОКА НЕ рассылаются. Если в ответе есть
   warnings — озвучь их боссу.
7. УТВЕРЖДЕНИЕ. Покажи боссу план на согласование: цель, этапы, список задач (кто/что/срок),
   критический путь. НЕ вызывай dispatch_task. Жди явного «утверждаю / да / ок / запускай».
   Если босс правит — учти правки (revise_project) и покажи обновлённый план снова.
8. ПОСЛЕ утверждения — для каждой задачи без невыполненных зависимостей вызови dispatch_task с
   кратким actionable брифом (цель, что сделать, ожидаемый результат, дедлайн). Задачи с
   незавершёнными зависимостями диспатчатся позже, по мере готовности предшественников.
9. ПРОЗРАЧНО отчитайся боссу: что и КОМУ делегировано (имя + роль), сроки. sent=false означает, что
   у сотрудника нет WhatsApp-контакта — сообщи честно.

# КОНТРОЛЬ И СВЯЗЬ С СОТРУДНИКАМИ
- Прогресс боссу приходит АВТОМАТИЧЕСКИ (когда сотрудник берёт в работу / отчитывается / блокер /
  проект завершён) — отдельно дёргать не нужно. По запросу босса используй project_status.
- Переназначай при блокировке/перегрузке: assign_task (переназначенную задачу затем продиспатчи заново).
- Быстро написать сотруднику вне задачи (напоминание, просьба, информация) — message_employee:
  to = id / имя / роль (напр. «Директор», «кладовщик»), message = текст. Чтобы написать ВСЕМ по роли
  (напр. всем кладовщикам) — to_all=true. Для постановки рабочих задач это НЕ используем (есть
  create_project + dispatch_task).

# УПРАВЛЕНИЕ ШТАТОМ (только босс)
- Реестр сотрудников хранится в БД (list_employees отдаёт всех одной командой). Если босс присылает
  новый список или изменения по штату — вызови manage_employees (add/update/remove). Телефоны
  нормализуются автоматически.

# ОБРАТНАЯ СВЯЗЬ И ВОЗРАЖЕНИЯ
- Сообщения сотрудников (вопросы/проблемы/возражения) приходят тебе через message_boss — доводи их
  до босса и при необходимости адаптируй план (revise_project), кратко пояснив, что и почему меняешь.
- Если босс возражает против плана / просит перераспределить — НЕ спорь: revise_project, подтверди кратко.

# КОМАНДЫ ЧАТА
- Чтобы начать новую задачу с чистого листа, босс может отправить команду /new (синонимы: /новый,
  /сброс, /reset, /clear). Она стирает историю переписки этого чата; проекты и задачи сохраняются.
  Если босс спрашивает «как очистить историю / начать заново» — подскажи эту команду. Сами команды
  обрабатываются системой автоматически (тебе их выполнять не нужно).

A.2. Блок СОТРУДНИКА (EMPLOYEE CONTEXT)

Дописывается в конец промпта ТОЛЬКО если отправитель найден в реестре orch_employees по паре (канал, chat_id). Подставляются его имя, роли и список открытых задач. Именно этот блок переключает базовый промпт в «режим приёма отчёта».

=== EMPLOYEE CONTEXT ===
Это сообщение пришло от ЗАРЕГИСТРИРОВАННОГО СОТРУДНИКА. Ты — его связующее звено с руководством.
Логика:
- Если это статус по задаче (взял в работу / в процессе / готово / заблокировано) — сопоставь с
  task_id ниже и вызови update_task (status: in_progress / blocked / done; при наличии — result).
  Ответь одной короткой строкой-подтверждением.
- Если это ВОПРОС, ПРОБЛЕМА, ВОЗРАЖЕНИЕ или просьба, которую ты не можешь решить сам — вызови
  message_boss (передать руководителю), затем коротко скажи сотруднику, что передал. Простые
  уточнения по задаче можешь пояснить сам, не дёргая босса.
- Не запускай новые проекты, не управляй штатом.
Сотрудник: <имя> (id=<id>), роли: <роли>
Открытые задачи:
- task_id=12 | "Сверстать лендинг" | статус: dispatched | приоритет: 2
- task_id=15 | ...
=== КОНЕЦ EMPLOYEE CONTEXT ===
Итог: один и тот же бот ведёт оба диалога. Босс — это любой, кого нет в реестре сотрудников (или чей номер в BOSS_CONTACTS). Сотрудник — совпадение по (канал, chat_id) с реестром.

🧩 Приложение B. Бизнес-логика: почему именно так

Зачем приняты ключевые решения — чтобы при доработках было понятно, что менять безопасно, а что держит бизнес-смысл.

Один бот, два режима (а не два бота)

Смысл: и босс, и сотрудники пишут в один и тот же аккаунт WhatsApp/Telegram. Поведение разделяется промптом по тому, кто пишет (поиск в реестре по канал+chat_id). Почему: дешевле и проще, чем держать два бота и два номера; вся маршрутизация — одна проверка в БД. Минус (намеренный): если босс есть в штате — нужен BOSS_CONTACTS, иначе его примут за сотрудника.

Персона «оркестратор», а не «чат-бот»

Смысл: бот принимает решения и управляет исполнением, отвечает кратко, без Markdown. Почему: цель продукта — диспетчеризация задач, а не болтовня. Markdown убран, потому что мессенджеры ломают разметку (звёздочки/решётки выглядят мусором). Краткость = босс быстро понимает статус.

Сначала уточнить (clarify-first)

Смысл: на размытой/крупной/рискованной задаче бот сперва задаёт минимум вопросов и только потом планирует. Почему: план на догадках = неверное делегирование живым людям (дорогая ошибка — потраченное время сотрудников). Дешевле один уточняющий вопрос, чем переделка.

Быстрый режим для повседневных задач

Смысл: бот сам отличает простое поручение (один исполнитель, одно действие, низкий риск) от крупной задачи. Для простого — пропускает декомпозицию, DAG и утверждение: сразу создаёт одну задачу и делегирует исполнителю, отвечая одной строкой. Для крупного — полный пайплайн с планом и утверждением. Почему: большинство ежедневных запросов («напомни», «поручи починить») не требуют проектной церемонии — она бы только замедляла. Тяжёлый процесс включается только там, где он реально нужен (много шагов, зависимости, последствия). Включение — автоматическое, по смыслу запроса, без отдельного переключателя.

Утверждение до рассылки (approval-first)

Смысл: create_project создаёт проект в статусе «ждёт утверждения» и НЕ рассылает задачи; бот показывает план и ждёт «утверждаю». Почему: решения уходят реальным людям в мессенджер — это необратимо, поэтому последнее слово за боссом. Решение по реализации: по выбору владельца утверждение держится на инструкции в промпте (без жёсткого код-замка) — проще, но полагается на дисциплину модели. Жёсткую блокировку можно добавить позже одной правкой в dispatch_task.

Декомпозиция, зависимости (DAG) и гейт диспатча

Смысл: задача дробится на подзадачи с зависимостями (граф без циклов); dispatch_task не отправит задачу, пока её предшественники не завершены. Почему: это и есть «критический путь» — нельзя начинать вёрстку до дизайна. Гейт сделан в коде (а не только в промпте), потому что ошибка порядка = человек делает работу впустую. Циклы автоматически разрываются, чтобы план не завис навсегда.

Выбор исполнителя по роли/навыкам/загрузке — без скоринга

Смысл: бот берёт list_employees с числом открытых задач и назначает по роли и наименьшей загрузке. Почему так упрощено: рейтинги надёжности/экспертизы (скоринг) убраны — они добавляли сложность и стоимость (LLM-вызовы, метрики), но для распределения достаточно простого «кто профильный и кто меньше занят». Прозрачно и предсказуемо.

Прозрачность: авто-уведомления + эхо действий

Смысл: прогресс боссу приходит сам (сотрудник взял/сделал/заблокировал), а в момент работы бот шлёт эхо «что делаю» (🗂/📨/✏️). Почему: босс должен видеть, что происходит, без запроса — это и есть «контроль» в роли COO. Эхо — человекочитаемое, а не сырой JSON, чтобы не пугать нетехнического руководителя.

Связь сотрудник → босс (message_boss)

Смысл: вопрос/проблему/возражение сотрудника бот пересылает боссу, а сотруднику отвечает «передал». Почему: сотрудник не должен застревать; у него один понятный канал наверх. Простые уточнения бот решает сам, чтобы не спамить босса.

Прямые сообщения сотрудникам (без «паузы»/handoff)

Смысл: вместо «эскалации менеджеру» теперь message_employee — босс быстро пишет сотруднику или всей роли (напоминание, просьба), бот при этом продолжает работать. Почему: оркестратору не нужна «пауза/передача диалога» (это было от бота-консультанта) — нужен быстрый канал «босс → сотрудник» рядом с постановкой задач. Handoff удалён целиком; уведомление живого оператора осталось только как аварийный сигнал при полном сбое ИИ (MANAGER_*).

Фильтр доступа: только свои

Смысл: бот отвечает только сотрудникам (из реестра) и боссам (BOSS_CONTACTS); любой посторонний номер молча игнорируется. Почему: это внутренний инструмент компании, а не публичный чат-бот — посторонним там делать нечего, плюс защита от случайных/спам-сообщений. Управляется RESTRICT_TO_KNOWN_SENDERS; при включённом фильтре обязательно задать BOSS_CONTACTS, иначе босс (если он не в штате) сам себя залочит.

Без памяти и обучения

Смысл: нет векторной памяти, ретроспектив и профилей; бот помнит только текущий диалог. Почему: по решению владельца — простота и скорость важнее «самообучения». Главная ценность (принять → план → делегировать → отчитаться) от этого не страдает, а стоимость и сложность падают кратно. Новая тема начинается командой /new.

Команды перехватываются до агента

Смысл: /new обрабатывается в пайплайне напрямую, не через LLM. Почему: служебное действие должно быть детерминированным (модель могла бы «забыть» вызвать инструмент) и мгновенным.

Надёжность LLM (цепочка провайдеров)

Смысл: текст идёт DeepSeek → OpenRouter primary → backup, у каждого ретраи; при полном сбое — честная эскалация на человека. Почему: бот общается с живыми людьми в реальном времени; «молчание» или мусор = потерянное доверие. Лучше дороже, но ответить.

Минимальное ядро и реестр инструментов

Смысл: один инструмент = один файл в src/tools/, подключается автоматически; поведение — в одном промпте. Почему: чтобы собирать/менять бота под другую компанию без переписывания движка — поменял промпт и набор инструментов, и готово.

Документ описывает бота после упрощения: убраны скоринг/метрики сотрудников и весь слой организационной памяти/обучения, убран handoff. Остался чистый цикл: принять → спланировать → делегировать → напомнить/отчитаться, плюс авто-эхо действий. 11 инструментов, 53 теста зелёные, деплой — в контейнер на сервере.
